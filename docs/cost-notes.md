# AI API 비용 구조 및 최적화 (2026-07-25 갱신)

## 결론 먼저

1. **다른 회사 "무료" API로 갈아타는 것은 권장하지 않음.** 웹 검색 도구(Recipe Scout), 이미지/URL에서 레시피 추출(Recipe Parser) 둘 다 특정 provider의 기능(Anthropic web_search 서버 도구, 비전 입력, 구조화된 JSON 출력 품질)에 묶여 있음. "무료" tier들은 요청 수/토큰 제한이 낮아서 사용자가 늘면 결국 유료로 전환해야 하고, 그 시점에 다시 마이그레이션 비용이 발생함.
2. **비용의 대부분은 토큰이 아니라 `web_search` 도구의 건당 수수료.** 따라서 지렛대는 (1) 캐시 적중률, (2) 검색 횟수 상한, (3) 무료 사용량 정책 — 이 세 가지뿐임. 토큰 최적화는 효과가 작음.
3. **Recipe Scout은 Pro 기능으로 전환됨** (2026-07-25). 무료는 하루 3회 맛보기.

## 실측: 검색 1건 비용 (2026-07-25, `max_uses: 2` 기준)

Haiku 4.5 가격: 입력 $1/MTok, 출력 $5/MTok. `web_search` 서버 도구는 검색 1회당 별도 과금(~$0.01/search).

| 쿼리 | 입력 | 출력 | 검색 |
|---|---|---|---|
| garlic butter shrimp pasta | 3,142 | 1,132 | 2 |
| kimchi fried rice | 3,133 | 1,049 | 2 |
| japanese ramen | 3,138 | 1,237 | 3→2 |
| chocolate chip cookies | 3,131 | 931 | 1 |
| **평균** | **~3,136** | **~1,087** | **~2** |

건당 비용:

| 항목 | 비용 | 비중 |
|---|---|---|
| 입력 토큰 | $0.0031 | 11% |
| 출력 토큰 | $0.0054 | 19% |
| 검색 수수료 (2회) | $0.0200 | **70%** |
| **합계** | **≈ $0.028** | |

**검색 수수료가 70%.** 토큰을 아무리 줄여도 검색 횟수와 캐시 적중률을 건드리지 않으면 비용은 거의 그대로임.

> 주의: `pause_turn` 연속 호출이 발생하면 대화 전체(검색 결과 포함)가 재전송되어 입력 토큰이 18,000까지 튀는 경우를 관측함(≈$0.018 추가). 드물지만 존재.

## 적용된 최적화

### 1. 캐시 TTL 3일 → 30일

3일은 대부분의 요리가 두 번째로 검색되기 전에 만료되어 절감분을 대부분 버리고 있었음. 웹의 "최고의 까르보나라 레시피"는 한 달 사이에 바뀌지 않으므로 체감 신선도 손실 없이 적중률만 올라감. 프롬프트가 바뀌어 결과가 실제로 달라져야 할 때는 `PROMPT_VERSION`이 즉시 전체 무효화하므로 TTL을 기다릴 필요 없음.

### 2. 캐시 키 정규화 강화

`best carbonara recipe`, `how to make carbonara`, `carbonara!` 가 각각 별도 항목으로 과금되고 있었음. 이제 filler(recipe/best/easy/how to make + 6개 언어 대응)와 문장부호를 제거해 하나의 키로 합침. 실측: 7가지 표기 → 1개 키.

**단어 순서는 일부러 유지함** — `chicken fried steak`와 `fried chicken steak`는 다른 요리라서 순서 무시 키는 잘못된 결과를 서빙하게 됨.

### 3. `max_uses` 3 → 2

지역 요리 쿼리로 재측정한 결과, 2회여도 "영어 1회 + 현지어 1회" 예산은 남아서 현지 소스 확보가 유지됨(라멘→Cookpad Japan, 김치찌개→10000recipe). 3회를 쓰던 쿼리만 2회로 줄어듦.

### 4. 캐시 실패가 조용히 돈을 새게 하던 버그 수정

postgrest는 테이블이 없을 때 예외를 던지지 않고 응답에 error를 담아 반환하는데, 코드가 `const { data } = ...`로 error를 버리고 있었음. **결과적으로 마이그레이션이 안 된 DB는 "캐시 미스"와 구분이 불가능했고, 모든 요청이 로그 한 줄 없이 full price를 지불함.** 이제 두 캐시 모두 테이블 부재를 명시적으로 경고함.

> **배포 전 필수 확인:** Supabase SQL Editor에서 `supabase/schema_07_search_cache.sql`(검색 캐시)과 `supabase/schema.sql`(추출 캐시)이 실행되어 있어야 함. 안 되어 있으면 위 최적화가 전부 무의미해짐. 이제 서버 로그에 `[searchCache] ... table does not exist ...`가 찍히므로 확인 가능.

### 5. Recipe Scout = Pro 기능 (2026-07-25)

검색은 추출과 달리 **그 자체로는 매출이 없는데 건당 비용은 가장 비쌈**. 익명 사용자에게 하루 15회를 열어두면 IP 하나당 하루 $0.42까지 노출됨.

- **무료(로그인 무관): 하루 3회** — Recipe Scout이 뭘 하는지 보여주고 구독을 결정하게 하는 맛보기
- **Pro: 하루 100회** — 제품 제한이 아니라 계정 공유/탈취 대비 백스톱
- 무료 한도 소진 시 `PRO_REQUIRED`(402)를 반환하고, 앱은 "내일 오세요" 대신 **Pro 구매 화면**을 띄움
- 무료 한도는 로그인 시 계정 단위, 비로그인 시 IP 단위로 계산 — 카페 wifi에서 남의 사용량에 내 3회를 뺏기지 않음

## 규모별 전망 (캐시 적중률에 따라)

건당 $0.028, 사용자당 하루 3회 검색 가정:

| 일간 활성 사용자 | 캐시 0% (마이그레이션 누락) | 캐시 50% | 캐시 70% |
|---|---|---|---|
| 100명 | $252/월 | $126/월 | $76/월 |
| 1,000명 | $2,520/월 | $1,260/월 | $756/월 |

무료 3회 정책 하에서는 위 표의 검색 횟수 자체가 크게 줄어들고, 초과분은 Pro 매출($4/월)로 상쇄됨. **Pro 구독자 1명 = 무캐시 검색 약 140회 분량의 비용을 커버.**

## 6. 검색 파이프라인 교체: Brave + Gemini Flash-Lite (2026-07-25)

### 왜

비용의 70%가 Anthropic `web_search` 도구의 건당 수수료($0.01)였음. **AI provider를 바꾸는 것으로는 나머지 30%(토큰)밖에 못 건드림** — 예를 들어 Claude를 Gemini Flash-Lite로만 바꿔도 $0.028 → $0.021(26% 절감)에 그침. 실제 지렛대는 **검색 자체를 더 싼 곳에서 하는 것**.

| | 검색 | AI | 건당 |
|---|---|---|---|
| 기존 | Anthropic web_search ×2 ($0.020) | Haiku 4.5 ($0.0085) | **$0.028** |
| 신규 | Brave ×1~2 ($0.005~0.010) | Flash-Lite (~$0.0008) | **$0.006~0.011** |

### 구조

`lib/ai/recipeSearch.ts`가 디스패처. `BRAVE_SEARCH_API_KEY`와 `GEMINI_API_KEY`가 **둘 다** 있으면 새 경로, 아니면 기존 Anthropic 경로.

1. **질의 계획** (`planQueries`, Flash-Lite) — 영어 검색어 + (지역 요리면) 현지어 검색어 생성. 토큰 몇백 개라 비용은 반올림하면 0. 예전에는 이 판단을 하려고 $0.01짜리 검색을 한 번 더 썼음.
2. **Brave 검색** — 영어 1회(count=20) + 현지어 1회(count=10, 지역 요리일 때만). `chocolate chip cookies`처럼 지역색 없는 요리는 1회로 끝남.
3. **순위/요약** (Flash-Lite) — 스니펫을 보고 실제 레시피 페이지만 골라 `RecipeSearchResult[]` 생성. 출력 스키마는 기존과 동일하므로 **UI는 변경 없음**.

### 안전장치

- **URL 화이트리스트**: 모델이 검색 결과에 없던 URL을 지어내면 전부 버림. 목업 테스트로 검증함(존재하지 않는 URL 주입 → 정상 거부).
- **자동 폴백**: 새 경로가 실패하거나 결과 0개면 Anthropic 경로로 재시도. 즉 Brave/Gemini 장애가 기능 중단으로 이어지지 않음. 단 이때는 **두 번 과금**되므로 로그에 `this costs more`로 크게 남김.
- **현지어 검색 실패는 치명적이지 않음**: 영어 검색 결과가 있으면 그대로 진행(폴백으로 새지 않게).
- **되돌리기**: 키 하나만 지우면 즉시 기존 경로로 복귀.

### 알려진 트레이드오프 (반드시 확인 필요)

Anthropic web_search는 **페이지 본문까지 읽고** 별점·리뷰 수를 가져왔지만, 새 경로는 **검색 스니펫(제목/URL/설명)만** 봄. 따라서 `highlights`("4.8★ · 2,340 ratings")가 이전보다 비어 있는 경우가 많아짐. 프롬프트에서 "스니펫에 없는 수치는 지어내지 말고 필드를 생략하라"고 강제했으므로 **틀린 숫자가 나오지는 않지만, 정보량은 줄어듦**.

> **미검증 상태:** 이 경로는 Brave/Gemini 키가 없어 실제 API로 테스트하지 못함(개발 샌드박스에서 Brave 호스트도 차단됨). 요청/응답 형태·중복 제거·URL 화이트리스트·HTML 제거는 목업으로 검증했으나, **실제 결과 품질은 키를 넣고 직접 비교해봐야 함.** 키를 넣은 뒤 같은 쿼리를 기존/신규로 몇 개 돌려보고 만족스럽지 않으면 키를 지우면 됨.

## 다음에 볼 만한 것 (아직 안 함)

- 출력 토큰 축소: 결과 5~7개 → 5개, `summary`/`whyGood` 중복 축소 → 출력 약 30% 절감(건당 ~$0.002, 전체의 6%). 효과 대비 품질 손실을 봐야 함.
- 언어별 캐시 분리 때문에 같은 요리가 6개 언어에서 6번 과금됨. 결과 URL은 언어 무관이므로 URL 목록만 공용 캐시하고 번역만 따로 하는 구조가 가능하지만, 번역에 또 호출이 필요해서 실익이 불명확함.
- 실사용 트래픽이 쌓이면 `search_cache.hit_count`로 실제 적중률을 측정해서 TTL과 무료 한도를 재조정.
